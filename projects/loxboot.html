Real scenarios

01

Pending firmware image

SituationAn update has been written to the inactive slot and awaits its first boot.

LOX Boot doesValidates persistent slot state and selects the pending image.

Observable resultLOX Boot validates state, selects the pending slot and leaves confirmation to the documented application flow.

02

Unconfirmed update

SituationThe new image resets before it confirms successful startup.

LOX Boot doesReads the missing confirmation state and applies the rollback-oriented selection rule.

Observable resultThe next boot follows the rollback-oriented slot state instead of repeatedly trusting the pending image.

03

Platform handoff

SituationThe core has selected a valid image on the target board.

LOX Boot doesReturns the selected image to the platform handoff adapter.

Observable resultThe platform adapter performs the board-specific jump while the portable core keeps policy state explicit.

Evidence here describes repository contents or explicitly recorded runs. It does not turn configured CI, compile-only checks or simulations into hardware validation.

Known limits

  • STM32 hardware is explicitly not verified
  • Board integration, flash layout and jump behavior remain platform work
  • It is a bootloader core, not an application-side crash-loop manager
