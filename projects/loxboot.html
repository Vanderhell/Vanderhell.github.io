What it solves

Firmware updates need validated slots, explicit handoff and rollback-oriented state.

A C99 bootloader core provides A/B state, UART update transport and adapter boundaries.

How it works

Dynamic architecture diagram
Reset → validate boot state → select A/B slot → platform handoff

Use it when

Receive an update over the supplied UART transport
Boot a pending image and require confirmation
Roll back an unconfirmed image on the next boot
Keep platform jump logic behind an adapter boundary

Engineering evidence

  • Host CMake and 20 CTest entries are documented as verified
  • ESP32-S3 ESP-IDF 5.5.1 build, flash, runtime and OTA/rollback runs are recorded in HARDWARE_EVIDENCE.md

Evidence here describes repository contents or explicitly recorded runs. It does not turn configured CI, compile-only checks or simulations into hardware validation.

Known limits

  • STM32 hardware is explicitly not verified
  • Board integration, flash layout and jump behavior remain platform work
  • It is a bootloader core, not an application-side crash-loop manager

Technical information

Public API and integration

Start with the public header shown in Quick Start and the repository documentation. Check every return value; storage, clock, transport and policy callbacks remain caller responsibilities where applicable.

Memory and concurrency

The repository documents no heap use for the library core; state is caller-owned. Shared-instance access is not claimed safe unless the repository explicitly provides a concurrency mode.

Build and configuration

The local repository provides its authoritative CMake/build configuration. Only supported integration paths shown there should be enabled.
