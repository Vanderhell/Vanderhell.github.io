What it solves

Producer and consumer code need a bounded queue with explicit ownership.

A fixed-capacity copy-based ring uses caller-owned storage, with optional constrained SPSC atomic mode.

How it works

Dynamic architecture diagram
Producer → copy into ring → consumer copy out

Use it when

Buffer fixed-size samples
Queue bytes between serialized tasks
Use one-producer/one-consumer atomic mode where supported

Quick Start

This minimum pattern is adapted from the repository README or public-header examples. Comments state the expected behavior; no terminal output is fabricated.

#include "mring.h"
static uint8_t storage[8*sizeof(sample_t)]; mring_t ring;
int rc=mring_init(&ring,storage,sizeof storage,8,sizeof(sample_t));
/* Expected: rc indicates a ready eight-element ring. */

Known limits

  • Default is single-context
  • Overwrite is unsupported in atomic mode
  • Snapshot queries need quiescence or synchronization in atomic mode

Technical information

Public API and integration

Start with the public header shown in Quick Start and the repository documentation. Check every return value; storage, clock, transport and policy callbacks remain caller responsibilities where applicable.

Memory and concurrency

The repository documents no heap use for the library core; state is caller-owned. Shared-instance access is not claimed safe unless the repository explicitly provides a concurrency mode.

Build and configuration

The local repository provides its authoritative CMake/build configuration. Only supported integration paths shown there should be enabled.
