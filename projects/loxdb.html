01 / THREE DATA MODELS

Choose a shape that fits the firmware

LOX DB puts several bounded data models behind one C interface. Each remains deliberately narrower than a server database: callers size storage and choose policies for their workload.

ENGINE 01

Key-value

Binary-safe values for configuration and application state, bounded by configured key and value limits. Optional TTL and compile-time overflow policy shape behavior at capacity.

ENGINE 02

Time-series

Typed streams for F32, I32, U32 and raw samples, with timestamp range queries and retention/overflow policies. Packed samples pair timestamps with values. The TS arena is divided evenly among configured stream slots, so mixed types do not use every byte equally efficiently.

ENGINE 03

Relational

Small fixed-schema tables with explicit schema declarations, row helpers and one indexed column per table. This is a compact record model, not general SQL planning or arbitrary joins.

One handle, explicit setup. lox_init() validates configuration and storage, creates internal arenas and loads durable state when storage is supplied. Normal engine operations do not churn the core allocator after successful initialization; ports and user callbacks have their own allocation behavior.
02 / MEMORY MODEL

Bounded arenas, one core allocation

The database targets MCU and edge systems where memory must be budgeted before normal work begins. Configuration chooses the main RAM budget and engine capacities. The core makes one main heap allocation during initialization and releases it at lox_deinit().

This statement is scoped to the core. Platform adapters, storage callbacks and application code may allocate independently. A bounded database arena does not bound total firmware memory unless those components are budgeted too.

Handles may be several KiB; the manual recommends keeping potentially large lox_t objects off small task stacks. Review profile and footprint gates for the exact build configuration.

03 / STORAGE ABSTRACTION

The media contract is a small HAL

Persistence is optional. A storage adapter supplies read, write, erase and sync callbacks through lox_storage_t. The abstraction lets the core work with RAM-backed and platform-backed media while keeping erase geometry and write constraints visible at initialization.

04 / WAL AND REOPEN

Recovery is a defined path, not a hardware guarantee

When WAL support is enabled with persistent storage, reopening validates durable state and applies documented recovery rules. The manual describes replay, handling recoverable WAL tails and compaction. Some anomalies can return success with recovery performed; success does not mean no anomaly occurred.

  1. Application mutation reaches an engine
  2. Configured persistence records durable state
  3. Reopen scans snapshot and WAL
  4. Documented replay or recoverable-tail handling restores state

What this evidence does not establish

The published ESP32-S3 benchmark uses an in-RAM flash-like storage backend. It measures target CPU work and logical backend operations, not physical NOR latency, brownout recovery, erase endurance or board-level power-loss behavior.

05 / PORTS AND PACKAGING

Core, adapters and distribution have separate jobs

Core library

The core is portable C99 with no required third-party runtime library. CMake exports an installable package as loxdb::loxdb; detached C and C++ consumer checks exercise installed-package use. A C++ convenience wrapper is separate from the C API.

Target integrations

RAM and POSIX ports, an ESP32 path and optional backend adapters cover different environments. Arduino and PlatformIO manifests publish the library through their registries. Hardware- or filesystem-specific behavior still depends on the chosen adapter and board.

08 / FIT AND BOUNDARIES

Where LOX DB is a good fit

Use the shape deliberately

  • It targets bounded embedded/edge data, not general SQL flexibility, advanced indexing or unbounded queries.
  • Relational tables are fixed-schema and support one indexed column per table.
  • There is no server-style multi-process concurrency model or transparent large-object storage.
  • The one-allocation statement describes the core after initialization, not adapters or callbacks.
  • WAL recovery tests and RAM-backed benchmarks do not establish physical flash, brownout or endurance behavior.
