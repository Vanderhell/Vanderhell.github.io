Real scenarios

01

MQTT link disappears

SituationTelemetry is produced while the broker cannot be reached.

iotspool doesPersists the message before asking the transport to deliver it.

Observable resultiotspool appends the message to persistent storage before delivery and keeps it pending.

02

Power loss with queued data

SituationThe device resets with unsent records in the spool.

iotspool doesMounts the queue and identifies valid records that remain pending.

Observable resultAfter restart, the queue recovers valid pending records and resumes caller-driven delivery.

03

Acknowledged delivery

SituationThe transport confirms that a queued record reached its destination.

iotspool doesCommits the acknowledged queue position through the configured backend.

Observable resultThe spool advances durable queue state so the acknowledged item is not sent as new work again.

Known limits

  • Uses an external MQTT client rather than implementing one
  • Durability depends on the selected storage backend contract
  • Application supplies time and publish-loop integration
